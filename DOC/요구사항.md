## 1. 개념 모델 (Domain Model)

### 1.1 엔티티 정의

#### 1.1.1 계약 (Contract)
- **정의:** 고객이 이용하는 통신 서비스 (5G 회선, 인터넷 등)
- **역할:** "무엇을 이용하고 있는가"
- **선/후불 구분:** 계약 단위로 결정
  - 후불 계약: 청구계정 연결 (월말 청구 → 인출일 결제)
  - 선불 계약: 청구계정 없이 정기결제 (구독형, 매월 동일일 결제)

#### 1.1.2 청구계정 (Billing Account, BA)
- **정의:** 매월 청구서 발송 단위 (채권 관리)
- **역할:** "누구에게 얼마를 받을 것인가"
- **특징:**
  - 1개의 청구계정 안에 여러 계약(회선) 포함 가능 (가족 통합 청구)
  - 인출일을 고객이 선택 (시스템 제공 고정 옵션 중 선택)
  - 명의자가 반드시 청구계정 소유주는 아님 (미성년 자녀의 계약을 부모 청구계정에 연결)
- **AS-IS와 차이:** 납부방법(PAY_MTHD_CD) / 계좌·카드 정보는 PAY_ACCT로 분리

#### 1.1.3 납부수단 (PAY_MEANS, "지갑")
- **정의:** 고객이 소유한 순수한 금융 결제 수단
- **역할:** "어떤 도구(수단)를 가지고 있는가"
- **종류:** 은행계좌, 신용카드, 간편결제 (카카오페이/네이버페이/토스페이 등)
- **독립성:** 청구계정/계약에 종속되지 않음. 웹 회원가입만으로도 시갑에 미리 등록 가능
- **비실명성:** 지갑 등록만으로는 결제 발생 안 함. 결제는 반드시 PAY_ACCT로 매핑되었을 때만.
- **명의:** 본인 명의 · 타인 명의 모두 등록 가능
  - 타인 명의일 경우 대리납부 앱립 테이블에 행 추가
  - 타인 명의 등록 시 계좌주/카드주에 대한 2차 인증 필요 (맛4금 [확정 필요])
  - 간편결제는 대리납부(타인명의) 불가 → 고객 본인만으로 등록 가능
- **인증 범위 (단독 등록 시):**
  - 은행/카드: 단순 실시간인증 (KS-NET/카드사) 수행
  - 간편결제: 별도 인증 없음 (고객 본인 확인만으로 등록)
- **자동납부 신청 진입 시:** 수단을 팝업으로 선택해도 신정 트랜잭션 안에서 재인증 (실시간 원장등록 인증) 수행.

#### 1.1.4 납부계정 (PAY_ACCT, "자동납부 약정서")
- **정의:** 특정 청구계정(후불) 또는 계약(선불)의 요금을 특정 납부수단으로 매월 인출하겠다는 동의(서)
- **역할:** "언제, 어떻게 돈을 뺄 것인가"
- **생성 조건:**
  - 후불 계약: 청구계정에 자동이체 납부방법 신청 시 생성
  - 선불 계약: 정기결제 신청 시 생성
- **보유 정보:**
  - 외부 금융기관(KFTC/SKVAN/PG)에 등록된 원장 정보
  - 간편결제 BILLKEY (간편결제 약정인 경우)
  - 출금동의증빙 (DRWAGR_PRF_TYP_CD/KEY)
  - 납부주기 · 인출일
- **메인/예비 납부수단:**
  - 메인 1개 + 예비 1개 (최대 2개)
  - 메인 인출 실패 시 예비는 월말/월초 일괄 배치로 결제 시도 (즉시 fallback 아님). 상세 BR-4.

#### 1.1.5 대리납부 맵핑 (PAY_AGENT_MAP)
- **정의:** 타인 명의 납부수단 사용 관계 명시
- **용어 정리:**
  - 대리납부자 = 납부수단 소유주 (계좌/카드의 실제 명의인). 돈이 빠지는 사람.
  - 피대리납부자 = 해당 수단을 자기 청구계정에 매핑하여 결제하는 사람. 혜택 받는 사람.
- **발생 조건:** 납부수단을 타인 명의로 청구계정에 매핑하여 발생 (≠ 청구계정 소유주 ≠ 대리납부자)
- **예시:** 부모 계좌(소유주=부모=대리납부자)를 자녀(피대리납부자)가 자기 청구계정에 매핑
- **다중성:** 한 납부수단을 여러 사람이 자기 청구계정에 매핑 가능 (1 수단 → N 대리납부 맵핑)
- **제한:** 간편결제는 대리납부 불가 (본인만 등록/사용 가능)

### 1.2 엔티티 관계 (ER 요약)

```
[고객] ─┬─ N → [계약]
        ├─ N → [청구계정] ─┐
        ├─ N → [납부수단]  │ (선불)          (후불)
        └─ N → [납부계정] ─┘─── 1 ─ N ───
                              │
                              ├─ 메인 (1) → [납부수단]
                              └─ 예비 (1) → [납부수단]

[납부수단] ── N ──→ [대리납부 맵핑] ←── 1 ── [피대리납부자]
   (납부수단 소유주=대리납부자 ≠ 청구계정 소유주=피대리납부자 일 때만 존재)
```

**관계 카디널리티 (방향별):**

| From | To | 관계 | 비고 |
|------|-----|------|------|
| 고객 | 납부수단 | 1:N | 한 고객이 여러 수단 보유 |
| 고객 | 청구계정 | 1:N | 한 고객 여러 청구계정 (가족 계정 분리 등) |
| 고객 | 납부계정 | 1:N | |
| 청구계정 | 납부계정 | 1:N | 후불. 1:N = 분리납부. 1.4 분리납부 룰 참조 |
| 계약(선불) | 납부계정 | 1:1 | 선불은 분리납부 불가, 항상 1:1 |
| 납부계정 | 납부수단 (메인) | N:1 | 한 수단을 여러 약정의 메인으로 사용 가능 |
| 납부계정 | 납부수단 (예비) | N:1 | 한 수단을 여러 약정의 예비로 사용 가능 |
| 납부수단 | 대리납부 맵핑 | 1:N | 타인 명의 시 사용처마다 행 |

### 1.3 핵심 비즈니스 룰

#### BR-1. 비실행성 (Non-Execution of Means)
- 납부수단이 지갑에 등록만 된 상태로는 어떤 인출/결제도 발생하지 않는다.
- 결제는 반드시 PAY_ACCT가 존재하고 그 PAY_ACCT가 활성 상태일 때만.
- 시스템 내 어떤 배치/실시간 모듈도 PAY_MEANS를 직접 송금 대상으로 삼지 않는다.

#### BR-2. 인증의 두 종류 + 진입 경로 3가지

**실시간 인증 2종:**

| 인증 종류 | 외부 호출 | 원장등록 동반 | 용도 |
|-----------|-----------|:---:|------|
| 단순 실시간인증 | KS-NET (계좌) / 카드사 (카드유효성) | × | 수단 단독 등록 시 유효성 검증 |
| 실시간 원장등록 인증 | EDI/FB/CMS (KFTC/SKVAN) + 카드사 | ○ | 자동납부 신청 시 약정 등록까지 트랜잭션 |

> CMS의 경우 인증 자체는 실시간이지만 원장등록은 D+1 배치로 분리됨. 신청 시점 흐름상으로는 "원장등록을 동반하는" 카테고리.

**진입 경로 3가지 (신청 흐름):**

| 경로 | 진입 화면 | 인증 종류 | PAY_MEANS | PAY_ACCT | 납부수단실시간인증 행 수 |
|------|-----------|-----------|-----------|----------|:---:|
| 경로 1 | 납부수단 관리 화면 (지갑) | 단순 실시간인증 | 신규 생성 | (생성 안 함) | 1 |
| 경로 2 | 자동납부 신청 화면 + 수단 직접 입력 | 실시간 원장등록 인증 | 신규 생성 | 신규 생성 (한 트랜잭션) | 1 |
| 경로 3 | 자동납부 신청 화면 + 팝업으로 등록된 수단 선택 | 실시간 원장등록 인증 (재인증) | 기존 수단 사용 | 신규 생성 | 2 (수단 등록 시 + 신청 시 재인증) |

**핵심:**
- 자동납부 신청은 AS-IS와 동일하게 한 트랜잭션으로 처리 (수단 + 약정 + 원장등록 한꺼번에)
- 경로 3의 경우 신청 시점에 수단 재인증 수행 (수단 상태가 등록 후 바뀌었을 수 있으니 재확인 + 원장등록 인증을 동반)
- 따라서 납부수단실시간인증 테이블은 같은 수단에 대해 N행 누적 가능 (등록 시 1행 + 신청 시 1행 + 변경 시 1행 …)
- 납부계정인증 테이블은 자동납부 신청/변경/해지 시점에만 행 생성 (약정 단위 이력)

#### BR-3. 외부기관 원장은 납부계정 단위
- 같은 은행 계좌(납부수단)라도 청구계정A용 PAY_ACCT와 청구계정B용 PAY_ACCT는 별개 원장.
- 따라서 PAY_ACCT별로 EDI/CMS/FB 등록 성공/실패 상태가 다를 수 있다.
- 외부기관에 같은 계좌로 여러 약정 등록 시 일부 실패 가능 (외부 기관 정책에 따라).

#### BR-4. 메인/예비 인출 순서 (★ 시간 분리)
- **STEP 1 — 정기 인출 (인출일 D-Day, 배치):** 메인 납부수단으로 인출요청
- **STEP 2 — 예비결제 (월말/월초 배치, 미수금 정리):** 메인 인출 실패분을 모아서 예비 납부수단으로 일괄 결제 시도
  - 적용 대상: 일반 (1:1) 납부계정 + 분리납부 적용 여부 미정 ([OI-17])
  - 카드는 이 시점에 실시간 카드승인 가능
- **즉시 fallback 아님** — 메인 실패 직후 바로 예비를 시도하지 않음. 한 달 동안 모았다가 월말/월초에 일괄 처리.
- 메인/예비 모두 실패 시 → 미납 처리 (재인출 룰은 영역 5에서 정의)

> 입력자료 원문("메인 실패 시 즉시 결제 시도")과 다름. 실제 구현은 월말/월초 일괄이 확정.

#### BR-5. 청구계정 명의 ≠ 결제 명의
- 청구계정 소유주가 반드시 통신 서비스 가입자는 아님 (미성년 자녀 사례).
- 마찬가지로 납부수단 소유주가 청구계정 소유주가 아닐 수 있음 (대리납부).

#### BR-6. 선불/후불 동치 처리
- 선불 계약과 후불 청구계정은 PAY_ACCT에서 동일하게 처리.
- 차이는 PAY_ACCT.선불후불구분코드 + PAY_ACCT.청구계정번호/계약번호 NULL 여부.
- 한 PAY_ACCT는 선불(계약번호로 채워짐) 또는 후불(청구계정번호로 채워짐) 중 정확히 하나에만 연결.
- 선불은 분리납부 불가능 → 선불 PAY_ACCT는 항상 계약과 1:1.
